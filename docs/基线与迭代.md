# 基线与迭代

本项目从经过脱敏的通用交付包独立安装，随后修复了真实账户接入中发现的多账户识别问题。用户已明确旧项目和旧数据都不沿用；后续使用和升级只在这里进行，不依赖旧仓库或旧打包材料。

## 目录职责

| 目录 | 放什么 |
|---|---|
| server-app | 可运行的程序、前端和 MCP |
| skills | 当前冻结的通用技能与来源证据 |
| workspace | 通用工作方法、空模板和规则更新记录 |
| private-runtime | 本机账户配置、Cookie、缓存和业务记录，禁止交付 |
| checks | 不使用真实账户的接入回归检查 |
| work | 本机启动辅助、检查过程材料，禁止交付 |
| docs、references | 程序契约、使用说明与版本边界 |

少数兼容模块仍可能在 server-app/cache 写本机缓存，该目录也按私有运行材料排除分发；当前账户画像和流量基线已配置到 private-runtime。不要把尚未重构的兼容路径说成已全部统一。

## 本轮已经验证

- 从独立空目录安装依赖，未继承旧 node_modules、旧数据库或旧策略。
- 真实 Cookie 的账户身份和原主计划核对一致，保存后的有效权限为 recommendation_only。
- MCP 可枚举 23 个工具；已实际验证账户状态、账户画像和一次总览读取，未逐一验收全部工具。
- 平台写入入口拒绝本轮未授权写入。没有进行实际投放修改。
- 修复了“多个直客账户”被误报 Cookie 失效，以及真实账户响应字段未识别的问题。

这些证据不等于功能齐全或全平台兼容。部分可选依赖安装脚本未获 npm 执行，长期连续盯盘、自动投放和所有页面均未全面验收。首页按需模式不自动查询连续采集指标。

## 新知识如何进入

1. 原资料先放入 workspace/规则更新/待整理，保留来源、发布日期、生效日期和适用投放类型。该目录内容默认不生效、不交付。
2. 将新旧规则逐项对照。先区分平台硬规则、经验建议和你自己的业务阈值；未知时间或适用范围保留待核实。
3. 把确认的差异记入“变更登记”，指定唯一的规则正文位置。其他入口引用该位置，不复制多份相互冲突的规则。
4. 每次只更新一个规则主题；若影响计算或执行，再更新相应程序和有意义的回归检查。不要用历史阈值自动填入你的新账户。
5. 先在本机只读验证并记录结果，再形成新版本。旧规则注明被哪份新规则替代；测试未通过时恢复已保留的版本。

当前技能是冻结的历史基线，不代表已经适配尚未整理的最新千川规则。新资料不得仅因日期较新就覆盖所有历史业务场景。

## 检查与分发

账户发现回归：在项目根目录运行 `node --require ./checks/setup-runtime.cjs --test checks/account-discovery.test.cjs`。检查使用空配置并阻止网络访问；运行材料留在 work，后续按授权移入回收站。

每次修改保留简短变更记录和验收结果。通用包由 `python tools/build_release.py` 在本项目内独立构建，最新位置见 release/latest.json。构建只读取 release/files.json 的白名单；本机 MCP 配置和自用说明改用 release/templates 下的通用模板，不读取 private-runtime 或旧项目。新文件经审阅后才加入清单，不使用“压缩整个自用目录”的方式交付。

本轮另通过首次自动安装、重复启动、空账户 MCP 引导和实际账户未开播检查。MCP 现在枚举 23 工具，新增 monitor_once；初始化与监控共有 17 项回归通过，之前账户发现 6 项通过。直播中的连续盘面、长期运行及各第三方客户端仍需实测。没有开启实际循环或定时任务。
