# 可迁移安全运行策略

本文件属于 `qianchuan-api` 的调用安全文档，为没有工作区专属策略的 Agent 提供只读降级与写入护栏。它只定义技术安全机制，不提供任何店铺的固定阈值，也不替代官方手册或账户策略。

## 一、运行模式

| 模式 | 条件 | 能力 |
|---|---|---|
| `recommendation_only` | 未校准、校准过期、数据质量异常 | 只读、计算、诊断、建议 |
| `confirm_writes` | Profile 已确认，但未授权自动写 | 每个具体写动作前请求一次人工确认；确认只绑定该对象、参数和 ROI 口径 |
| `auto_guarded` | Profile 已确认且显式授权 | 仅在 Profile 护栏内自动写 |

新账户和未指定模式的任务固定从 `recommendation_only` 开始。模式升级必须由用户明确确认，不能由模型自行推断。不可逆操作、主计划停删、越权对象和服务端要求人工确认的动作，在任何模式下都不能自动执行。

## 二、账户 Profile

账户 Profile 保存“该账户事实和校准值”，至少包括：
- 账户 ID、名称、主播/直播间身份、主计划 ID；
- 明确 `roi_basis` 的保本线、利润参考线、风险观察线；
- 各漏斗阶段的历史基线、样本量、可比窗口；
- 按接口真实渠道 code 保存的看播/成交占比历史基线；未知 code 不补渠道标签；
- 主播可持续基础流速、追投流速和总流速容量；
- 最小消耗、点击和订单样本门槛；
- 主播、商品、价格机制和时段等可比条件；
- 平均客单价、常用直播排班；
- ROI 调整冷却、受保护对象、写权限；
- 每个校准值的来源与更新时间，以及 Profile 整体确认人和状态。

旧版 Profile 缺少新字段时可以安全读取，但只能降低判断置信度：缺漏斗基线就不宣称断点显著，缺容量就不自动放量，缺样本门槛就保持观察。不得为补字段而伪造 0 或跨账户阈值。

所有账户数值都必须标记来源。来源分为：
- `official`：平台公开机制；
- `runtime_config`：服务配置或后台回读；
- `historical_calibration`：目标账户历史数据反推；
- `human_confirmed`：用户人工确认；
- `task_override`：用户当前任务明确覆盖。

## 三、默认监控流程

没有工作区覆盖时：
1. 先用 `load_account_profile(account_id)` 读取安全 Profile 子集；不存在或结构化失败时降级为 `recommendation_only`；
2. 再读 `get_live_view(level="status")`；
3. `isLive=false` 时停止盘面读取，转低频待命；
4. 在播且数据有效时读 `get_live_view(level="dashboard")`；
5. 记录当前快照，并与上一份同口径快照计算真实跨度差分；
6. 异常先定位“付费进入 → 停留 → 商品点击 → 支付 → 退款/结算”的首个断点，再区分责任域；
7. 只在聚合数据不足以支持具体决策时追加一个专项读取。

不要把实际 7 分钟差分写成 5 分钟。单个在线人数是瞬时截面，不做趋势归因；只有同场、同定义、带来源时间的连续快照才能计算在线变化，并且必须与流速、商品点击、订单、GMV和GPM联合判断。

## 四、数据质量门

任一条件成立时降级为只读：
- Cookie 失效或账户未认证；
- 账户、主播或房间身份不匹配；
- `netDataValid=false` 或 `costDataValid=false`；
- `roi_basis=unknown` 或 Profile 阈值与计划目标口径不一致（仅阻断 ROI 写入）；
- 快照时间陈旧，或连续快照没有新数据；
- 订单、GMV、消耗发生无法解释的口径切换；
- Profile 缺少保本线或目标对象 ID。

累计 ROI 是滞后指标，只作背景。支付、平台 1 小时净、最终结算和乘方综合 ROI 必须分列；任何调控至少结合真实同口径区间边际、消耗流速和数据质量。

## 五、决策输出

公共默认只输出以下内容：
- 当前累计消耗、同口径 GMV、ROI、订单、`roi_basis` 与结算窗口；
- 真实跨度区间的消耗、同口径 GMV、订单、边际 ROI、流速；
- 计划、追投和 Top 素材的当前状态；
- 依据 Profile 阈值形成的建议；
- 数据质量、模式、读取次数和写入次数。

异常时固定增加：漏斗断点、责任域、责任岗位、首个经营动作、投放动作或阻断原因、验证窗口。

不把固定行业倍数直接变成写操作。平台建议、算法分数和历史经验只能作为旁证。

## 六、写操作闭环

写前：
1. 确认运行模式和对应权限；
2. 确认账户、主计划/追投/素材 ID；
3. 检查最新数据、冷却和用户手动状态；
4. 说明预期影响与退路；
5. 核对写入参数与目标对象的 `roi_basis`；
6. `confirm_writes` 每次取得用户对具体动作的确认。

写后：
1. 保存服务端回执与成功时间；
2. 回读对象状态；
3. 用 Profile 定义的样本门槛和可信可比区间验证实际效果；
4. 无效则撤销或停止继续加码；
5. 结论写入账户经验，不提升为通用机制，除非经过跨账户验证。

## 七、覆盖关系

用户当前任务可以覆盖：轮询频率、简报格式、账户阈值、调控矩阵、排班和自动化权限。

用户当前任务不能绕过：
- MCP Schema；
- Cookie/身份/数据新鲜度检查；
- 用户手动状态保护；
- 不可逆操作确认；
- 提交后回读与后验。

固定倍率、固定 ROI、固定预算和固定时长只能保留在有来源的案例卡中。当前接口不支持的品牌广告、云图、Feed/人群定向和乘方写操作标为 `blocked`；机制尚未验证但可做对照的内容标为 `experiment_only`。
