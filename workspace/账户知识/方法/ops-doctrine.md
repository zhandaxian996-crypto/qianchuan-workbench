# 千川持续盯盘决策纪律

来源性质：工作区通用方法卡，改编自 `弈/账户知识/方法/ops-doctrine.md`。状态：`adopted_core`；执行模式与实时写入部分在本包降级为只读建议。

持续任务遵循“验真—判断—建议—复核”闭环。状态不能由记忆、人格、旧会话或本地经验推断；真实数据与当前 Schema 高于历史 Lesson、评分和常识。

## 1. 三阶段

场前 `pre_live`：确认目标口径、消耗/GMV/订单/流速、计划与冷却、素材池、追投候选、救场和放大条件、验证窗口与回滚。多商品场至少按完整讲品周期记录商品顺序和可比窗口。身份或数据冲突时区分当前值、历史值和建议值，阻断依赖它的动作。

盘中 `in_live`：读取真实窗口边际，先看数据质量，再按“付费进入 → 停留 → 商品点击 → 支付 → 退款/结算”定位首个断点。对齐主播、商品、价格/券/库存、话术、素材、计划、追投和控量事件；多变量同时变化时标记混杂。常规素材清理留到场后，盘中只形成紧急且可逆候选。

场后 `post_live`：确认下播后停止调整，锁定场次身份，按有效的 `roi_basis/settlement_window` 完成该口径结论。无效、占位 0 或子项失败时补读允许的场次/回放来源，缺口仍存在就带缺口结束，不无限等待。常规清理只建议移出，不物理删除。

## 2. 执行模式

本包固定 `recommendation_only`：只读、判断、留痕和给建议，不调用投放写工具，不创建平台投放任务，不暂停/删除对象，不启动心跳。`confirm_writes` 与 `auto_guarded` 只作未来接入名称，必须由客户在另一任务中明确授权并核验权限，不能被模板填写绕过当前只读边界。

## 3. 每轮十二步

1. 验证账户、场次键、直播状态、时间、`dataValid/stale/partial/errors`、口径和结算窗口。
2. 按读取纪律取同口径边际与基础/追投拆分；短窗口发现变化，主窗口确认持续。
3. 比较计划目标与真实边际，拆分基础/追投输入，结合连续在线、点击、订单、GMV、GPM 判断是否稀释候选。
4. 对齐事件时间线，记录同窗的主播、商品、价格、话术、素材和计划变化。
5. 找到漏斗首个断点；缺字段或结算未回流先标数据链路。
6. 使用原始渠道名，分列看播人数、成交人数、金额及占比，缺失保持 `null`。
7. 在素材、主播承接、商品价格、计划、追投、数据链路中选主责任域并列备选。
8. 先给经营动作，再给投放建议，不用调 ROI 代替修商品或数据。
9. 只选择一个可逆候选；条件不足时说明保持现状理由。
10. 若未来执行，写前核验 Schema、模式、Profile、对象、口径、冷却、预算、并发和回滚。
11. 执行后回读真实状态和 `operation_id`；本包当前跳过执行，保留为边界。
12. 绑定 snapshot/session 留痕，区分相关性和因果，不调用退役评分或自动经验链路。

每轮最多一个动作候选，等待下一可信窗口后再评估；不连环追改。

## 4. 防守与进攻

防守：扩量稀释以客户策略的服务端状态和同口径证据为准；画像/渠道单场漂移且效率健康先观察；单素材空耗先形成候选；多素材共同走弱且边际持续低于策略线才考虑计划层；主播和商品异常归经营责任域。样本不足或口径不一致只做专项诊断。

进攻：只有身份、数据、边际、容量和权限可信且流速确实欠饱和时，才形成单步释放或赢家放大候选。一两单或短时高 ROI 只证明能成交，不证明可规模化；需验证独立窗口、更多入口、商品承接和重复路径。

## 5. 证据边界

支付、平台净、最终结算和乘方综合 ROI 分列；兼容字段名不证明最终结算。真实 0 需要 `dataValid=true`。代理模型不能称为平台内部算法。接口不支持的品牌广告、云图、Feed/人群定向和乘方写操作标为 `blocked`；未知机制只能 `experiment_only`。
